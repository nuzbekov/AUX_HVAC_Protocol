# Python-реализация протокола

Кодер/декодер UART-протокола кондиционеров AUX и скрипт опроса COM-порта.
Всё сделано строго по [описанию протокола](../README.md) в корне репозитория:
там, где протокол не расшифрован, байты отдаются сырыми, а гипотезы помечены
в docstring'ах и не выдаются за факты.

Отдельно разобран [интерфейс RS485](#rs485) — это совсем другой протокол,
а не тот же самый на другой физике. Кадровый уровень расшифрован, из
данных — состояние блока и два датчика температуры.

## Установка

Библиотека и `aux_tool.py` работают на голом Python без зависимостей
(нужен 3.8 или новее; проверялось на 3.14).
Для работы с реальным портом нужен `pyserial`:

```
pip install -r python/requirements.txt
```

## Проверка протокола без железа

`aux_tool.py` ничего не открывает и никуда не лезет — им удобно проверять
кодек и разбирать дампы.

```
python aux_tool.py selftest
```

Прогоняет 123 проверки по всем примерам пакетов из README: контрольные суммы,
пересборку кадров байт в байт, разбор полей статусов, мутаторы состояния,
потоковый разборщик и автоответы клиента. Возвращает 0, если всё сошлось.

Разбор кадра:

```
python aux_tool.py decode "BB 00 07 00 00 00 18 00 01 21 C0 3D 00 02 54 3A 00 29 \
    00 00 00 00 00 00 00 00 00 00 00 00 00 05 10 36"
```

```
[<=] INFO CMD=OUTDOOR [BB 00 07 00 00 00 18 00] 01 21 C0 3D ...
      внешний блок: ВКЛ, режим COOL, в комнате 26.5°C, снаружи н/д,
      вентилятор LOW, мощность 0%, ошибка: нет ошибки
```

Ключ `--bits` добавляет побайтную раскладку с двоичным представлением —
удобно, когда разбираешься с очередным нерасшифрованным битом.
Ключ `--json` даёт машиночитаемый вывод.

Сборка команды:

```
python aux_tool.py encode control --power on --mode cool --temp 22.5 --fan auto --raw
BB00068000000F000101700080A00020000020000000001DBD
```

Контрольная сумма для произвольного набора байт:

```
python aux_tool.py crc BB 00 06 80 00 00 02 00 11 01
CRC:    2B 7E   (CRC1=0x2B, CRC2=0x7E)
```

Разбор записанного дампа — понимает и текстовый лог в формате README
(со скобками, метками направления и комментариями после `#`), и сырой
бинарник:

```
python aux_tool.py replay examples/sample_log.txt
python aux_tool.py replay line.bin --binary --summary
```

## Опрос кондиционера

```
python aux_poll.py --list                 список COM-портов
python aux_poll.py -p COM6 --loopback     проверка адаптера
python aux_poll.py -p COM6                пассивное прослушивание
python aux_poll.py -p COM6 --active       эмуляция wifi-модуля
python aux_poll.py -p COM6 --json --log ac.jsonl
python aux_poll.py -p COM6 --dump line.bin
python aux_poll.py -p COM6 --monitor      живая панель состояния
python aux_poll.py -p COM6 --watch        только изменения (кнопки ИК-пульта)
python aux_poll.py -p COM6 --status       разовое чтение статуса
python aux_poll.py -p COM6 --set --power on   разовая команда
```

**Пассивный режим** (по умолчанию) молча слушает линию между штатным
wifi-модулем и сплитом. Ничего не передаёт, поэтому безопасен.

**Активный режим** (`--active`) сам изображает wifi-модуль: отвечает на
дежурные ping-пакеты, отвечает на пакеты инициирования и раз в `--interval`
секунд запрашивает статус внутреннего и внешнего блоков.

> **Важно.** Активный режим нельзя включать, если к линии уже подключён
> штатный wifi-модуль: два «модуля» на одной линии будут перебивать друг друга.

`--dump line.bin` пишет сырой поток в файл, который потом разбирается офлайн
через `aux_tool.py replay line.bin --binary`. Это самый удобный способ собрать
материал по нерасшифрованным байтам.

### Живая панель: `--monitor`

```
python aux_poll.py -p COM6 --monitor
python aux_poll.py -p COM6 --monitor --monitor-interval 0.5
```

Опрашивает оба статуса раз в секунду и держит на экране состояние списком,
перерисовывая кадр **на том же месте**, а не печатая его следом. Изменившиеся
строки на несколько секунд помечаются `<-- изменилось`.

```
AUX HVAC — монитор   COM6  4800/8-E-1   13:42:35   опрос 1.0 с   Ctrl+C — выход

ВНУТРЕННИЙ БЛОК (CMD=0x11)
----------------------------------------------------------------
  питание                    ВКЛ
  режим                      COOL
  целевая температура        26.0 °C
  вентилятор задан           HIGH
  TURBO                      ВКЛ                    <-- изменилось
  ...
  тело статуса               97 E0 01 20 00 20 00 00 20 00 00 00 00

ВНЕШНИЙ БЛОК (CMD=0x21)
----------------------------------------------------------------
  температура, байт 15+31    22.9 °C
  теплообменник, байт 17     57  (25 °C по T-0x20)
  ошибка                     0x0E — E4: нет обратной связи двигателя ...
```

Панель занимает альтернативный буфер экрана, как это делают `top` и `htop`:
основная прокрутка терминала не трогается, и по выходе вы видите ровно то, что
было до запуска — последний кадр печатается ещё раз, чтобы состояние осталось
перед глазами. Кадр обрезается по размеру окна, а если окно мало, последняя
строка сообщает, сколько строк скрыто; растяните окно, и панель развернётся.

Перерисовка требует ANSI. На Windows виртуальный терминал в консоли включается
автоматически при запуске; если терминал его не поддерживает или вывод
перенаправлен в файл, кадры просто идут друг за другом — режим не ломается.

Рядом с «сырыми» значениями показаны номера байтов, чтобы панель можно было
сверять с описанием протокола, не заглядывая в код.

### Разбор кнопок ИК-пульта: `--watch`

```
python aux_poll.py -p COM6 --watch
```

Печатает **только изменившиеся** байты — с именем, в двоичном виде и с
расшифровкой состояния. Нажимаете кнопку на пульте и сразу видите, какой бит
поехал.

Отдельно отслеживается счётчик минут в байте 12: его обнуляет любая команда с
пульта, поэтому по нему видно сам факт приёма ИК-команды, даже если ни один
другой байт не изменился. Это отличает «кнопку контроллер не понял» от
«кнопка принята, но ничего не делает».

> Оговорка: если нажать вторую кнопку в ту же минуту, счётчик уже нулевой и
> обнулять нечего. Поэтому режим ещё и опознаёт ИК-команду по изменению любого
> байта настроек, а когда счётчик поднимается выше нуля, печатает строку
> «можно нажимать следующую кнопку». Кнопки, которые ничего не меняют, надёжно
> ловятся только после этой строки.

Байты температур скрыты как шум, показать их — `--all`.

### Разовые команды: `--status` и `--set`

```
python aux_poll.py -p COM6 --status
python aux_poll.py -p COM6 --set --power on --mode cool --temp 23.5
python aux_poll.py -p COM6 --set --fan low
python aux_poll.py -p COM6 --set --byte 18=0x80
```

`--set` читает статус, правит только то, что названо ключами, отправляет
команду, проверяет CRC в подтверждении и печатает побайтную разницу обоих
статусов. Одна команда — один наблюдаемый эффект, после чего скрипт
завершается. Это удобнее непрерывного прогона, когда доказательством служит
поведение платы: видно, где начинается и заканчивается шаг.

`--byte N=V` пишет произвольный байт тела (10..22) — для проверки
нерасшифрованных полей. Сочетается с остальными ключами.

### Как читать вывод

`[=>]` — кадр ушёл в линию, `[<=]` — пришёл из линии. В активном режиме
запросы видны сразу, ещё до того как кондиционер ответит:

```
08:44:50 [=>] CMD CMD=INDOOR  [BB 00 06 80 00 00 02 00] 11 01 2B 7E
08:44:53 [<=] PING            [BB 00 01 00 00 00 00 00] 43 FF
08:44:53 [=>] PING            [BB 00 01 80 01 00 08 00] 1C 27 ... 1E 58
```

Если строки `[=>]` идут, а `[<=]` нет — скрипт исправен, проблема на стороне
линии. Через 15 секунд тишины он сам об этом скажет. Проверять по порядку:

1. **исправен ли адаптер** — см. `--loopback` ниже;
2. **общая ли земля** с платой кондиционера;
3. **не перепутаны ли TX и RX** на линии до кондиционера;
4. **есть ли кому отвечать** — без штатного wifi-модуля кондиционер сам шлёт
   только ping раз в ~3 с, а на запросы статуса отвечает лишь когда линия
   подключена к его разъёму модуля.

### Проверка адаптера

`--loopback` отделяет неисправность адаптера, драйвера или параметров порта
от проблем с линией до кондиционера. Замкните на адаптере TX и RX и запустите:

```
python aux_poll.py -p COM6 --loopback
```

Отправленный кадр обязан вернуться и разобраться:

```
Отправляю: BB 00 06 80 00 00 02 00 11 01 2B 7E
Принято 12 байт: BB 00 06 80 00 00 02 00 11 01 2B 7E

Эхо совпало с отправленным, кадр разобран. Адаптер, драйвер и
параметры порта (4800/8-E-1) исправны.
```

Код возврата 0 при успехе и 1, если эха нет или байты пришли искажёнными
(так бывает при неверной скорости или чётности).

Если перемычку забыть снять, в обычном режиме собственные кадры вернутся из
линии и будут помечены `<- эхо` — распознаётся сверкой с только что
отправленным, а не по содержимому, поэтому кадры настоящего wifi-модуля при
пассивном прослушивании за эхо не принимаются.

## Использование как библиотеки

Прослушивание линии:

```python
from aux_hvac import AuxClient, SerialTransport

with AuxClient(SerialTransport("COM6")) as client:
    client.on_state = lambda state, packet: print(state.describe())
    client.run(duration=60)
```

Управление. Штатная последовательность из README — запросить статус,
поправить нужные биты, отправить обратно командой `TYPE=0x06 CMD=0x01`:

```python
from aux_hvac import AuxClient, Mode, FanSpeed, SerialTransport

with AuxClient(SerialTransport("COM6"), active=True) as client:
    client.request()                      # запрос статуса внутреннего блока
    client.run(duration=5)                # ждём ответ
    state = client.indoor.copy()
    state.set_power(True).set_mode(Mode.COOL).set_target_temp(23.5)
    state.set_fan_speed(FanSpeed.AUTO)
    client.apply(state)
```

Мутаторы `set_*` правят сырые байты тела и возвращают сам объект, поэтому их
можно сцеплять. Всё, что не тронуто, уезжает обратно в кондиционер без
изменений — включая нерасшифрованные байты.

Разбор одного кадра:

```python
from aux_hvac import Packet, decode_state

packet = Packet.decode(bytes.fromhex("bb000700000018000121c03d..."))
print(packet.describe())
print(decode_state(packet).to_dict())
```

## Что осталось нерасшифрованным

Библиотека не прячет незнание. Нерасшифрованные байты доступны через
`state.unknown`, а сомнительные трактовки помечены в docstring'ах:

* **байт 17 (To)** внешнего блока — достоверной формулы нет, отдаётся сырым
  (`return_temp_raw`) плюс гипотеза Brokly `T - 0x20` (`return_temp_hint`);
* **байт 14 (FPWM)** — README расходится сам с собой в том, брать ли биты 1..7
  или байт целиком; отдаётся сырой байт;
* **бит VL байта 11** и **бит DS байта 20** у части моделей инвертированы;
* **байт 29** — из кодов ошибок достоверно известен только `0x07` (E5),
  остальные значения в таблицу намеренно не занесены.

## RS485 — шина центрального управления

Это **отдельный протокол**, а не UART-протокол на другой физике. Общего нет
ничего: другая скорость, другой стартовый байт, другая контрольная сумма,
другая структура тела. Гипотеза «нагрузка совпадает с UART-вариантом»
проверена прямо и **опровергнута**: 13-байтовое тело статуса внутреннего
блока не укладывается ни в один срез нагрузки, разбор даёт заведомый мусор
вида «режим 0x07, вентилятор 0x07, таймер 28:16».

Разобрано на дампе шины контроллера фанкойла AUX.

Совпадение CRC с CRC16/MODBUS наводит на мысль, не отвечает ли плата ещё и
на стандартный Modbus RTU параллельно со своим протоколом — платы на общей
прошивке иногда так умеют. Проверено `modbus_probe.py`: функции 0x01/0x02
(катушки/дискретные входы) и 0x03/0x04 (holding/input регистры), адреса
`0x00` (широковещательный), `0x01`, `0xF1`, `0xF0`, `0xE1`, `0xC1`, `0xC2`,
`0xCF` — все адреса, что-либо говорившие на шине, — регистры `0..16`
(и отдельно `0..64` для `0x01`), количества `1, 2, 4, 8`. Ни одного ответа,
похожего на Modbus RTU. Совпадение CRC — просто совпадение (или общая
библиотека внутри прошивки), а не признак совместимости на уровне кадра.

### Параметры линии

**9600/8-N-1.** Подтверждено тем, что на этой скорости все 65 кадров дампа
сошлись по CRC. Направлением приём/передача управляет сам чип адаптера,
поэтому со стороны программы это обычный последовательный порт.

### Формат кадра

```
7E  A  B  CMD  LEN  <нагрузка>  CRC_lo CRC_hi
|   |  |  |    |                |
|   |  |  |    |                +-- CRC16/MODBUS, младший байт первым
|   |  |  |    +------------------- длина ВСЕГО кадра, включая 7E и CRC
|   |  |  +------------------------ код команды
|   +--+--------------------------- два адреса
+---------------------------------- стартовый байт
```

* **CRC16/MODBUS** (отражённый полином `0xA001`, начальное значение `0xFFFF`,
  без финального XOR) считается от байта **сразу после** `0x7E` и до байтов
  CRC. Сошлось 65 из 65 кадров;
* **LEN** — длина всего кадра вместе со стартовым байтом и CRC;
* порядок байт разный: CRC — little-endian, значения регистров —
  big-endian. Это не опечатка, так в линии.

### Нагрузка: блок регистров

У всех кадров, которые несут данные, нагрузка устроена одинаково:

```
<индекс> <кол-во> <кол-во 16-битных значений big-endian>
```

то есть `len(payload) == 2 + 2 * count`. Сходится точно на всех кадрах с
данными, включая самый большой: индекс 3, 17 регистров, 2 + 34 = 36 байт.

Значения знаковые, в десятых долях градуса. Значение `-100.8` в регистре 7,
похоже, означает «датчик не подключён»: на стенде часть датчиков
действительно не подключена.

### Кадр `CMD=0x01` — состояние блока

Этот кадр под модель «индекс, количество» не подходит, и поначалу разбор
выбрасывал его целиком. Оказалось, что состояние блока лежит именно в нём:

| где | что | как проверено |
|---|---|---|
| байт 0, бит 7 | питание | сопоставление с UART |
| байт 0, биты 6..4 | режим | 5 значений из 5 |
| байт 0, биты 3..1 | скорость вентилятора | 4 значения из 4 |
| байт 0, бит 0 | качание шторок | сверено с UART |
| байт 1, бит 7 | дисплей | сверено с UART |
| байт 1, бит 2 | SLEEP | сверено с UART |
| байты 2..3 | уставка, десятые доли, big-endian | 5 значений из 5 |
| байты 4..5 | не расшифровано: 0 и 5 | — |

Байт 0 расшифрован целиком. Бит 0 поначалу считался всегда нулевым — он и
был нулевым, пока в опыт не добавили шторки: при включении качания байт шёл
`0x9A` → `0x9B`.

**TURBO в этом кадре нет вовсе.** Он виден только в регистре 7 кадра
`CMD=0x02`: при включении регистр менялся ровно на `0x0100`, то есть бит 8.
Там же оказались бит 7 (SLEEP) и бит 13 (качание шторок). Сам регистр 7
раньше принимали за температуру, а его значение `-100.8` — за «датчик не
подключён»; на самом деле это набор флагов.

Проверка всех трёх на живом железе, оба интерфейса одновременно:

```
SLEEP вкл    UART: sleep=True  turbo=False шторки=SWING | ШИНА: SLEEP=True  TURBO=False качание=True
TURBO вкл    UART: sleep=True  turbo=True  шторки=SWING | ШИНА: SLEEP=True  TURBO=True  качание=True
всё выкл     UART: sleep=False turbo=False шторки=STOP  | ШИНА: SLEEP=False TURBO=False качание=False
```

**Коды режима и скорости те же, что в UART-протоколе**, только сдвинуты на
один бит: в UART они занимают биты 7..5 своих байтов, здесь — 6..4 и 3..1.
Поэтому перечисления `Mode` и `FanSpeed` переиспользуются как есть.

Проверка на живом железе, оба интерфейса одновременно:

```
задано: 27.5°C, FAN, HIGH
  UART : вкл=True, режим 6, вент 1, уставка 27.5°C, дисплей вкл, в комнате 25.2°C
  ШИНА : вкл, режим FAN, вентилятор HIGH, уставка 27.5°C, дисплей вкл,
         ROOM 25.2°C, PIPE 24.8°C
```

Сходится всё, включая половину градуса. Собирает это `BusState`:

```python
from aux_hvac.rs485_protocol import BusState, RS485Decoder

state = BusState()
for frame in RS485Decoder().feed(data):
    state.update(frame)
print(state.describe())
```

Величины, которых в пришедших кадрах не было, остаются `None`, а не нулём:
иначе «выключено» не отличить от «ещё не приходило».

### Расшифрованные регистры

Опыт: снять дамп, изменить **одну** величину, снять второй дамп, сравнить.
Так опознаны два регистра кадра `CMD=0x02`:

| регистр | что это | как установлено |
|---|---|---|
| 10 | датчик `ROOM`, комната | за обе записи гулял в пределах `24.9…25.3` — живой датчик, а не константа |
| 13 | датчик `PIPE`, теплообменник | прогрев феном поднял `24.7` → `74.0`, и **только** его |

Отсюда же следствие, важное для UART-протокола: **по шине RS485 температура
теплообменника отдаётся с разрешением 0,1 градуса**, тогда как в байте 17
UART-протокола тот же датчик лежит с разрешением 1 градус. Нужны десятые
доли — берите их с RS485.

Остальные регистры за оба опыта не изменились, поэтому имён у них нет.
Догадки, которые в код намеренно **не** занесены: регистры 11 и 12 держат
`20.0` и похожи на уставку, регистры 4, 5 и 6 держат `29.0`, `32.0` и `19.2`
и похожи на границы диапазонов. Регистры 16 и 17 (`14081` и `6404`) на
температуры не похожи вовсе.

Подписи регистров привязаны к команде, а не только к номеру: блоки разных
команд по номерам перекрываются — кадр `CMD=0x12` тоже содержит регистры
10…13, но они там нулевые, и датчиками не являются.

Короткие кадры `CMD=0x55` с нагрузкой `00 00 11` под эту модель не подходят
и разбираются как есть — похоже, это опрос или keepalive.

### Адреса и цикл обмена

Встретились `F1`, `F0`, `E1`, `C1`, `C2`, `CF`, `01`, `00`. Старший полубайт
похож на класс устройства, младший — на номер экземпляра. В парах
запрос-ответ адреса меняются местами (`F1 01` → `01 F1`), но **какой из двух
байт источник, а какой получатель, пока не определено**: во всём цикле
первым байтом идёт `F1`, и только у опроса адреса `E1` первым стоит `01`.
Поэтому поля названы нейтрально, `addr_a` и `addr_b`.

Цикл повторяется без изменений:

```
F1 01  CMD=55   опрос
01 F1  CMD=02   ответ: 17 регистров, среди них температуры
F1 00  CMD=A1
F1 F1  CMD=12   три кадра: блоки регистров с индексами 10, 23 и 46
F1 F0  CMD=A5
01 E1  CMD=55   опрос
F1 C1  CMD=55   опрос
F1 C2  CMD=55   опрос
F1 CF  CMD=55   опрос
F1 01  CMD=55   опрос
01 F1  CMD=01   короткий ответ
```

Отвечает только адрес `01`, остальные опрашиваемые молчат — на стенде их
физически нет.

### Управление: почему его тут нет

ИК-приёмник стоит на дисплее фанкойла — казалось бы, естественно ожидать, что
именно `F1` в ответ на нажатие пульта что-то пишет в `01`. Проверено прямо:
запись шины во время нажатий (`--rs485 -v --dump`), под запись — включение,
смена режима DRY→HEAT, изменение уставки, выключение. Каждое нажатие честно
поменяло состояние — оно видно в очередном ответе `01 F1 CMD=01`:

```
 12: 01->F1 cmd=01  DRY,  выкл, уставка 26.0
 34: 01->F1 cmd=01  DRY,  вкл,  уставка 26.0    <- включили
 56: 01->F1 cmd=01  HEAT, вкл,  уставка 24.0    <- сменили режим
100: 01->F1 cmd=01  HEAT, вкл,  уставка 25.0    <- подняли уставку
122: 01->F1 cmd=01  HEAT, выкл, уставка 25.0    <- выключили
```

Но **ни разу, ни на одном из четырёх нажатий, в дампе не появилось ни
единого нового кадра** — ни от `F1`, ни тем более от чужого адреса. Весь
цикл между этими строками бит в бит совпадает со штатным опросом. Новое
значение просто появляется в очередном ответе `01`, как будто оно возникло
само.

Вывод отсюда только один: **ИК-приёмник подключён напрямую к плате `01`, в
обход этой шины и в обход `F1`.** Дисплей на корпусе — чисто пассивный
индикатор: он лишь периодически спрашивает `01`, что показывать, и не
участвует в исполнении команд пульта никак. На этой шине принципиально
не бывает кадра записи, потому что среди участников цикла нет ни одного
устройства, которое хоть когда-нибудь пишет, — а значит, обнаружить формат
команды управления, слушая шину, нельзя ни при каком количестве дампов:
её здесь никто не подаёт.

Практический итог: **чтение по RS485 работает полностью и надёжно**
(состояние, обе температуры, TURBO, SLEEP, качание шторок — см. выше).
**Управление по этой шине недостижимо** без физического вмешательства
в схему — например, врезки в линию ИК-приёмника или в шлейф между
дисплеем и платой, если он там вообще есть отдельно от RS485. Ни то ни
другое этот репозиторий не покрывает.

### Как снимать и разбирать

```
python aux_poll.py -p COM9 --rs485                     слушать шину
python aux_poll.py -p COM9 --rs485 --monitor           живая панель регистров
python aux_poll.py -p COM9 --rs485 --dump rs485.bin    слушать и писать дамп
python aux_tool.py rs485 rs485.bin                     разобрать дамп офлайн
```

Дампы, на которых всё разобрано, лежат рядом — железо для проверки не
нужно. Второй снят после прогрева датчика `PIPE` феном, и сравнение
показывает ровно тот опыт, которым расшифрован регистр 13:

```
python aux_tool.py rs485 examples/rs485_bus_fancoil.bin
python aux_tool.py rs485 examples/rs485_bus_fancoil.bin \
                   --diff examples/rs485_bus_fancoil_pipe_hot.bin
```

Построчный режим печатает только новые и изменившиеся кадры (`-v` — все):
цикл повторяется, и в потоке одинаковых строк настоящее изменение регистра
теряется. Изменившийся кадр помечается `*`.

`--monitor` рисует панель на месте, как `top`, и обновляет её раз в секунду
(`--monitor-interval`). Шину при этом только слушаем: на ней уже есть
мастер, и опрашивать самим не нужно — поэтому период здесь означает период
перерисовки, а не период опроса.

Что в панели:

* по разделу на каждый блок регистров, с адресами, командой, диапазоном
  регистров и счётчиком кадров;
* расшифрованные регистры подписаны названиями;
* изменившееся значение помечается `<-- изменилось` на 5 секунд — этим
  удобно искать регистр, не снимая двух дампов;
* кадры без блока регистров (опросы) сведены в один компактный раздел в
  конце: иначе они занимают по разделу каждый и панель перестаёт влезать в
  окно.

Градусы в панели показываются **не у всех** регистров. У расшифрованных —
всегда, у остальных — только если значение попадает в правдоподобный для
датчика диапазон. Иначе ноль превращался бы в «0.0 °C», а значение 17 — в
«1.7 °C», то есть панель выдавала бы догадки за показания. Полный набор
значений без этого фильтра даёт офлайновый разбор `aux_tool.py rs485`.

Дамп можно писать и одновременно с панелью: `--monitor --dump` работают
вместе.

### Что ещё не известно и как это выяснить

1. **Смысл остальных регистров.** Есть два способа, и второй быстрее в
   разы.

   **Через два дампа.** Снять запись, изменить **одну** величину, снять
   вторую запись, сравнить:

   ```
   python aux_tool.py rs485 до.bin --diff после.bin
   ```

   Вывод покажет только изменившиеся регистры, с разницей в градусах и без
   повторов. Так расшифрованы регистры 10 и 13. Минус очевиден: один
   регистр за пару дампов.

   **Через сопоставление с UART** — см. [ниже](#correlate). У платы два
   интерфейса, и семантика известна у одного из них. Слушая оба сразу,
   каждое изменение любой величины сразу даёт пару «известное поле —
   неизвестный регистр».
2. **Кто источник, а кто получатель** в паре адресов.
3. **Смысл команд.** `0x55` — опрос, `0x01` и `0x02` — ответы разной длины,
   `0x12`, `0xA1`, `0xA5` — передача блоков регистров.
4. **Запись.** Есть ли команда записи регистра — неизвестно, и, похоже, узнать
   это с этой шины нельзя в принципе, см. [«Управление: почему его тут
   нет»](#rs485-control). Поэтому `request_status()` кадр собирает
   (формат-то известен), а функций управления в модуле нет вовсе: угадывать
   код команды, которая что-то меняет в контроллере, — плохая идея.
   `parse_status()` по той же причине по-прежнему бросает `NotDecodedYet`:
   давать регистрам правдоподобные имена пока не на чем.

### Сопоставление регистров с полями UART

Ключевая мысль: у платы **два интерфейса одновременно** — разъём
wifi-модуля, где протокол расшифрован весь, и шина RS485, где почти ничего.
Если слушать оба сразу, то каждое изменение любой величины немедленно даёт
готовую пару «известное поле UART — неизвестный регистр шины». Одна сессия
закрывает столько регистров, сколько величин успели подвигаться, вместо
одного регистра за пару дампов.

Нужны два переходника: один на разъёме wifi-модуля, второй на клеммах A/B.

```
python aux_poll.py --sweep     -p COM6 --rs485-port COM9   активный проход
python aux_poll.py --correlate -p COM6 --rs485-port COM9   пассивно, крутите пульт
```

`--sweep` не ждёт, пока величины подвигает человек: он двигает их сам, по
одной за шаг, и после каждого шага печатает, что на шине поехало. Причина
изменения при этом однозначна. Двадцать шагов занимают около двух минут и
дают сразу всю таблицу выше.

Меняются только уставка, режим, скорость вентилятора, дисплей и питание —
то есть то же, что делает пульт.

По UART скрипт работает активно — изображает wifi-модуль и запрашивает
статусы, по шине только слушает: там уже есть свой мастер. Период запроса по
умолчанию даёт 7 секунд на каждый вид статуса, ровно как в эталонной
реализации [GrKoR/esphome_aux_ac_component][ref]
(`AC_STATES_REQUEST_INTERVAL = 7000`).

[ref]: https://github.com/GrKoR/esphome_aux_ac_component

Панель показывает найденные соответствия, регистры, которые двигались, но ни
с чем не сошлись, и подсказку, какие величины ещё не трогали. Дальше нужно
просто крутить пульт: уставка, режим, скорость, шторки, включение.

Как считается соответствие. Каждое правило здесь появилось после того, как
его отсутствие дало ложную находку на живом железе:

* **считать по снимкам нельзя** — шина повторяет цикл, и сотня снимков это
  те же двадцать состояний. Поэтому снимки группируются по значению поля
  UART, и группа даёт один голос;
* **брать самое частое значение в группе нельзя** — оно прячет редкие, но
  настоящие состояния. Регистр 200 при включённом питании почти всегда равен
  64, а в нагреве 128, и правило большинства выдало «бит 6 = питание». Берётся
  значение, на котором регистр **устоялся**: по второй половине наблюдений
  группы. Переходные снимки всегда в начале — там, где UART уже обновился, а
  шина ещё нет;
* **соответствие должно быть взаимно однозначным.** Одностороннее — не
  расшифровка: у того же регистра 200 бит 6 равен нулю сразу при двух
  значениях, в том числе при включённом питании;
* **порог точный.** Всё, что не сошлось полностью, идёт в отдельный список и
  прямо называется догадкой. Проверено: верные соответствия дают 100%,
  ложные — 90..91%, и скидка даже в один процент возвращает находки вида «бит
  регистра с комнатной температурой = питание»;
* поле или регистр, которые за сессию не менялись, не сопоставляются ни с
  чем: с постоянным значением совпадёт что угодно;
* проверяются не только значения целиком, но и **битовые поля внутри них** —
  питание, режим и скорость на шине упакованы в один байт, и целиком такой
  байт ни с чем не совпадёт. Одно и то же место, описанное и как бит слова, и
  как бит байта, схлопывается к байтовому описанию;
* масштаб проверяется 1, 10 и 2: UART отдаёт градусы и половины, шина —
  десятые доли;
* **величина должна измениться вместе с полем хотя бы дважды.** У поля с
  двумя значениями почти любой бит успевает совпасть один раз. Считать
  переходы по соседним снимкам при этом нельзя: поле меняется в одном
  снимке, шина догоняет в следующем, и переход не попадает в счёт вовсе —
  скорость вентилятора, изменённая четыре раза, давала один переход. Поэтому
  наблюдения разбиваются на отрезки постоянного значения поля, и переходы
  считаются между отрезками;
* **одно место не может означать две разные величины.** Если на него
  претендуют два несовпадающих поля, хотя бы одно объяснение ложно, и оба
  уходят в догадки. Так отсеялось «бит 13 регистра 7 = питание», заявленный
  одновременно как положение шторок. Одна величина под двумя именами
  противоречием не считается;
* **внутри опознанной температуры флаги не ищутся.** Датчик плывёт
  непрерывно, младшие биты щёлкают часто, и двухзначный флаг рано или поздно
  попадёт с ними в такт: так появилось «бит 1 регистра 13 = дисплей», хотя
  регистр 13 — это датчик PIPE.

Отчёт честно перечисляет, чего сделать не удалось: что двигалось, но не
сошлось, и для каких полей места не нашлось. Неверно подписанный регистр
хуже неподписанного — его перестают проверять.

`--log` пишет снимки в JSONL, так что разбор можно повторить или уточнить
позже, не переснимая сессию.

### Артефакты линии

Перед каждым ответом адреса `01` в дампе стоит одиночный байт `0xFE`, не
входящий ни в один кадр. Похоже на огрызок от переключения направления
RS485: передатчик поднимает драйвер чуть позже начала стартового бита, и
приёмник видит обрубок. Сами кадры при этом целы, CRC сходится, а такие
байты попадают в счётчик `dropped_bytes`.

## Тесты

```
python tests/test_protocol.py
python -m unittest discover tests
```

Зависимостей нет: тесты на stdlib `unittest`, pytest их тоже подхватывает.
Помимо прогона `selftest` они перебирают все температуры с шагом 0,5 °C, все
сочетания режима и скорости вентилятора, все положения шторок, дробят поток
на куски всех возможных размеров и проверяют, что CRC ловит любую одиночную
ошибку бита в кадре.

Кадровый уровень RS485 проверяется на реальном цикле обмена, снятом с шины:
разбор без единой ошибки CRC, пересборка кадров байт в байт, дробление
потока, устойчивость к огрызкам от переключения направления линии и к
мусору, а также то, что нерасшифрованная часть по-прежнему честно бросает
`NotDecodedYet`.
